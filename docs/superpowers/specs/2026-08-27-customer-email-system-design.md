# Hermes Customer Email System Design

## Goal

Deploy a production email system for Hermes that provides:

- reliable account-verification and password-reset messages from the Railway-hosted application;
- a real `support@hermesruns.com` Gmail inbox for customer conversations;
- replies that show only the Hermes support identity, never the owner's personal Gmail address;
- authenticated sending, bounded credentials, and delivery diagnostics without exposing tokens or customer data.

## Current state

The Spring Boot backend already implements email-verification and password-reset flows through `EmailVerificationService` and `PasswordResetService`. Both currently depend on Spring Mail and SMTP configuration. Railway Hobby blocks outbound SMTP, so those services cannot be enabled safely in production by adding `SPRING_MAIL_*` variables alone.

The production design therefore replaces application SMTP with Resend's HTTPS API. Google Workspace owns the human support mailbox and is not called by the Hermes backend.

## Scope

This slice includes:

- one Google Workspace Business Starter mailbox at `support@hermesruns.com`;
- Cloudflare DNS records required by Google Workspace for mail receipt and authenticated human replies;
- a separate Resend sending domain at `mail.hermesruns.com` for automated Hermes messages;
- a domain-restricted, sending-only Resend API key stored in Railway;
- an HTTPS transactional-mail adapter in the Spring Boot backend;
- verification and password-reset templates with `support@hermesruns.com` as Reply-To;
- deployment, delivery, authentication, and regression checks.

Marketing campaigns, newsletters, inbound-email ingestion by Hermes, a custom support-ticket dashboard, attachments, and bulk sending are out of scope.

## Architecture

### Human support channel

Google Workspace receives and sends human support mail for `hermesruns.com`. The licensed Workspace user is `support@hermesruns.com`; the owner opens it beside the personal Gmail account with Gmail's account switcher. Customer replies remain in the Workspace mailbox, so the personal Gmail address is never placed in message headers.

The root domain uses Google's MX record and Google-provided DKIM selector. Root-domain SPF authorizes Google Workspace. DMARC begins in monitoring mode and is tightened only after delivery reports confirm that every legitimate sender aligns.

### Transactional channel

Resend owns only the `mail.hermesruns.com` sending subdomain. Automated messages use:

- From: `Hermes <no-reply@mail.hermesruns.com>`
- Reply-To: `support@hermesruns.com`

Using a subdomain isolates transactional-sender reputation and DNS authentication from the human Workspace mailbox. Resend's SPF, DKIM, and return-path records are installed exactly as generated by the Resend dashboard.

### Application transport

Introduce a focused `TransactionalMailSender` contract in the backend. `ResendTransactionalMailSender` implements it with an HTTPS client and the Resend email API. `EmailVerificationService` and `PasswordResetService` construct their domain-specific messages and delegate delivery through that contract.

The implementation must not fall back to SMTP in production. Development may use a no-send adapter only when the production profile is not active. Removing the `spring-boot-starter-mail` dependency and obsolete `SPRING_MAIL_*` production configuration is part of the migration once no runtime code depends on `JavaMailSender`.

## Configuration

Railway stores these values as service variables:

- `RESEND_API_KEY`: sending-only key restricted to `mail.hermesruns.com`;
- `APP_MAIL_FROM`: `Hermes <no-reply@mail.hermesruns.com>`;
- `APP_MAIL_REPLY_TO`: `support@hermesruns.com`;
- `APP_PUBLIC_BASE_URL`: `https://hermesruns.com`;
- `APP_MAIL_PROVIDER`: `resend`.

The API key is never committed, copied into frontend code, emitted in logs, or exposed through readiness endpoints. Production startup fails closed when mail is required but the provider key, sender, Reply-To address, or public base URL is incomplete.

## Message data flow

### Account verification

1. Signup creates the existing random verification token and stores only its hash and expiry.
2. `EmailVerificationService` builds a link under `https://hermesruns.com/api/auth/verify-email`.
3. `TransactionalMailSender` submits plain-text and HTML alternatives to Resend over HTTPS.
4. The response message identifier may be logged for diagnostics; the token and API key must never be logged.
5. Existing signup rollback semantics remain unchanged in this slice so the transport migration does not alter authentication behavior.

### Password reset

1. The existing endpoint returns the same generic response whether or not the address exists.
2. The service stores only the reset-token hash and expiry.
3. The email links to `https://hermesruns.com/reset-password`.
4. Existing rate limiting and one-hour expiry remain unchanged.

### Customer support

1. A customer sends mail to `support@hermesruns.com`.
2. Google Workspace receives it directly through the root-domain MX record.
3. The owner replies from the Workspace Gmail mailbox.
4. The customer sees `support@hermesruns.com`; Hermes and Resend do not process or store the conversation.

## Reliability and error handling

- The HTTPS client has explicit connect and request timeouts.
- Resend `429` and `5xx` responses are treated as temporary delivery failures; other `4xx` responses are configuration or payload failures.
- Each delivery uses an opaque idempotency key so a bounded retry cannot create duplicate messages. Tokens and recipient addresses are not embedded in that key.
- Automatic retries are limited to one retry for temporary failures. Endpoint behavior remains bounded and does not wait indefinitely.
- Logs contain event type, provider message ID when available, HTTP status, and a one-way recipient fingerprint. Logs exclude plaintext tokens, reset links, API keys, and message bodies.
- Provider error bodies are sanitized before logging or returning an application error.

## Security

- Require a passkey or hardware-backed two-step verification for the Workspace account.
- Store Workspace recovery codes outside Gmail and outside the Hermes repository.
- Use a Resend key with sending-only access restricted to `mail.hermesruns.com`.
- Rotate the Resend key after suspected exposure and verify the previous key is revoked.
- Publish SPF and DKIM before enabling DMARC enforcement.
- Start DMARC at `p=none`, review reports for at least one week, then move gradually to quarantine and reject.
- Keep the existing Cloudflare Access protection for `admin.hermesruns.com`; mail setup does not weaken or bypass it.

## DNS plan

Cloudflare remains authoritative for `hermesruns.com`.

1. Verify domain ownership in Google Workspace with the Google-provided TXT record.
2. Add Google's root-domain MX record and activate Gmail.
3. Add root-domain SPF and Google DKIM records.
4. Add the initial `_dmarc.hermesruns.com` monitoring policy.
5. Verify `mail.hermesruns.com` in Resend and add only the DNS records generated for that subdomain.
6. Do not alter the existing apex, `www`, or `admin` web-routing records.

No provider-generated DNS value is guessed. Every record is copied from the active Google Workspace or Resend setup screen and verified after propagation.

## Deployment sequence

1. Purchase or start the Google Workspace Business Starter trial and create `support@hermesruns.com`.
2. Verify the domain and activate Gmail through Cloudflare DNS.
3. Enable two-step verification and confirm inbound and outbound support mail.
4. Create the Resend account, verify `mail.hermesruns.com`, and create a domain-scoped sending key.
5. Implement and test the Resend HTTPS adapter locally with a non-production recipient.
6. Add Railway variables without exposing their values in chat or repository files.
7. Deploy the backend and verify account verification and password reset against production.
8. Review DMARC reports before raising enforcement.

## Verification

### Backend checks

- focused unit tests for request serialization, headers, Reply-To, timeouts, idempotency, and sanitized error handling;
- controller/service regressions for signup verification, resend verification, generic password-reset responses, and rate limits;
- backend compile and targeted Maven tests;
- production startup fails when the selected provider is partially configured.

### DNS and mailbox checks

- public DNS resolves the expected Google MX, Workspace SPF/DKIM, DMARC, and Resend subdomain records;
- a message from an unrelated external account reaches `support@hermesruns.com`;
- a Workspace reply reaches that external account with no personal Gmail address in visible or reply headers;
- delivered support mail passes SPF, DKIM, and DMARC.

### Transactional checks

- verification and password-reset messages reach at least Gmail and Outlook test recipients;
- links use `https://hermesruns.com` and expire according to current backend rules;
- delivered messages pass SPF, DKIM, and DMARC alignment for `mail.hermesruns.com`;
- Resend delivery logs show accepted messages while Railway logs contain no credentials or plaintext tokens;
- `https://hermesruns.com`, `www` redirection, and Cloudflare Access on `admin.hermesruns.com` remain unchanged.

## Acceptance criteria

The work is complete when customers can email and receive replies from `support@hermesruns.com`, automated verification and reset messages are delivered from `no-reply@mail.hermesruns.com` through Resend's HTTPS API, all sender-authentication checks pass, secrets exist only in managed provider configuration, and the live website and protected admin hostname pass their existing production checks.
