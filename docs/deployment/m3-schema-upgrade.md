# Schema upgrade: best efforts and same-route runs

This release adds two columns to `activities` and two tables. Production runs Hibernate in `validate` mode
(`APP_JPA_DDL_AUTO=validate`), so the app **refuses to boot** until the schema matches. Run the SQL below **before**
deploying the new build, after [the effort and zones upgrade](m1-schema-upgrade.md) if that has not been run yet. Local H2
databases (`ddl-auto=update`) need nothing.

## The change

```sql
BEGIN;

-- Which route group a run belongs to (route_match_group below), and which version of the run analysis (best efforts and
-- route matching) last ran for it. Both are NULL until the run has been analysed. Neither is a foreign key: a group and a
-- run can be deleted in either order.
ALTER TABLE activities ADD COLUMN IF NOT EXISTS route_match_group_id bigint;
ALTER TABLE activities ADD COLUMN IF NOT EXISTS records_version integer;
CREATE INDEX IF NOT EXISTS idx_activity_route_match_group ON activities (route_match_group_id);

-- A route a runner has run: where it started and finished, how far it went and which way round.
CREATE TABLE IF NOT EXISTS route_match_group (
    id              bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    runner_id       bigint           NOT NULL REFERENCES runner (id),
    start_latitude  double precision NOT NULL,
    start_longitude double precision NOT NULL,
    end_latitude    double precision NOT NULL,
    end_longitude   double precision NOT NULL,
    distance_meters double precision NOT NULL,
    bearing_degrees double precision,
    winding         integer          NOT NULL,
    is_loop         boolean          NOT NULL,
    created_at      timestamp(6)     NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_route_match_group_runner ON route_match_group (runner_id);

-- The fastest stretch of one standard distance inside one run. One row per run and distance.
CREATE TABLE IF NOT EXISTS activity_best_effort (
    id                     bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    activity_id            bigint           NOT NULL REFERENCES activities (id),
    runner_id              bigint           NOT NULL REFERENCES runner (id),
    distance_key           varchar(12)      NOT NULL,
    distance_meters        double precision NOT NULL,
    elapsed_seconds        double precision NOT NULL,
    start_offset_seconds   integer,
    end_offset_seconds     integer,
    estimated              boolean          NOT NULL,
    edited_elapsed_seconds integer,
    effective_seconds      double precision NOT NULL,
    hidden                 boolean          NOT NULL,
    local_date             date             NOT NULL,
    model_version          integer          NOT NULL,
    CONSTRAINT uk_activity_best_effort UNIQUE (activity_id, distance_key)
);
CREATE INDEX IF NOT EXISTS idx_abe_runner_distance_time ON activity_best_effort (runner_id, distance_key, effective_seconds);
CREATE INDEX IF NOT EXISTS idx_abe_runner_distance_date ON activity_best_effort (runner_id, distance_key, local_date);

COMMIT;
```

The statements are idempotent, so running them twice is harmless. The column and table definitions were taken from the
JPA mappings (`Activity`, `RouteMatchGroup`, `ActivityBestEffort`), not written by hand. Types matter: `validate`
rejects `smallint` for a field mapped as an integer.

## After the deploy

Nothing has to be run by hand. A run's best efforts and route are worked out when the run is imported, when its stream
arrives, and in the background after every start: up to 500 runs per start, newest first
(`app.records.catchup-on-startup`, `app.records.catchup-max-runs`). Reading a run's records, or the Profile page's best
efforts or personal records, also analyses the runs that have not been, up to 100 per request and for at most 1.5 s, so a
runner who opens the app after the deploy sees their records fill in without waiting for a restart. There is no
administrator job. To analyse a very long history in one go, raise `APP_RECORDS_CATCHUP_MAX_RUNS` for one start (each run
costs one read of its points); lower it, or set `APP_RECORDS_CATCHUP_ON_STARTUP=false`, on a server that cannot spare the
time. Raising `BestEffortService.MODEL_VERSION` in a later release analyses every run again the same way.

## What behaves differently after deploying

- The run page has a **Best efforts** card (the fastest stretch of 15 standard distances, with the place of each among all
  the runner's runs, a chip time that can be typed in, and a way to hide an effort) and a **Same-route runs** card.
- The Profile page has a **Best efforts** analysis: the three best ever and the ten best of a year at a distance, and the
  best time of every year (`GET /api/training/best-efforts`).
- The Profile page's personal records (1 km, 3 km, 5 km, 10 km, half marathon, marathon) are read from the stored best
  efforts instead of being worked out from every run's points on each request. They come out close to what they were, with
  two differences: a chip time a runner typed counts and an effort they hid does not, and the search is now exact between
  readings and ignores a stretch that is a GPS jump, so a time can differ by a second or two from before. Until a run has
  been analysed it holds no record.
- The account export has a new file, `best-efforts.csv`. Deleting a run or the account deletes its efforts.
- `activities` gains two columns that are not part of the API response.

## Rolling back

Roll the app back first, then (only if you need to) drop what was added:

```sql
DROP TABLE IF EXISTS activity_best_effort;
DROP TABLE IF EXISTS route_match_group;
DROP INDEX IF EXISTS idx_activity_route_match_group;
ALTER TABLE activities DROP COLUMN IF EXISTS route_match_group_id;
ALTER TABLE activities DROP COLUMN IF EXISTS records_version;
```

Leaving them in place is safe for the previous build, because Hibernate's `validate` mode ignores extra columns and
tables. If you roll back for good, drop `activity_best_effort` and `route_match_group`: their foreign keys to `activities`
and `runner` would block any code that hard-deletes a run or a runner.
