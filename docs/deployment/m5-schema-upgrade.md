# Schema upgrade: run type and tags

This release adds one column to `activities` and one table. Production runs Hibernate in `validate` mode
(`APP_JPA_DDL_AUTO=validate`), so the app **refuses to boot** until the schema matches. Run the SQL below **before**
deploying the new build, and after the earlier upgrades the same build also needs, if they have not been run yet:
[M0](m0-schema-upgrade.md), [M1](m1-schema-upgrade.md) and [M3](m3-schema-upgrade.md) (the fitness curve and the weekly
effort of this release add no schema of their own). Local H2 databases (`ddl-auto=update`) need nothing.

## The change

```sql
BEGIN;

-- What kind of run the runner says it was: RACE, LONG_RUN or WORKOUT, or NULL for none. A label for the runner's own use;
-- nothing is computed from it. Not part of the API response of the list of runs.
ALTER TABLE activities ADD COLUMN IF NOT EXISTS run_type varchar(16);

-- A word the runner put on one of their runs. A run holds a few (at most six), each once however it is capitalised:
-- label_key is the lower-case form two spellings share, label is how the runner wrote it.
CREATE TABLE IF NOT EXISTS activity_tag (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    activity_id bigint       NOT NULL REFERENCES activities (id),
    runner_id   bigint       NOT NULL REFERENCES runner (id),
    label       varchar(64)  NOT NULL,
    label_key   varchar(64)  NOT NULL,
    created_at  timestamp(6) NOT NULL,
    CONSTRAINT uk_activity_tag UNIQUE (activity_id, label_key)
);
CREATE INDEX IF NOT EXISTS idx_activity_tag_runner_key ON activity_tag (runner_id, label_key);

COMMIT;
```

The statements are idempotent, so running them twice is harmless. The definitions were taken from the JPA mappings
(`ActivityRelationshipFields.runType`, `ActivityTag`), not written by hand. Types matter: `validate` rejects `char(16)` or
`text` for a field mapped as `varchar(16)`, and `timestamp` without a precision for a `LocalDateTime`.

Checked on 2026-10-10 on a throwaway PostgreSQL 17.10 (the schema this build expects, minus what this document adds, so
not on a copy of production): this build refuses to boot with `validate` before the SQL and boots after it; the result is
Hibernate's own schema apart from the order of two columns and the names of the two foreign keys; running it twice changes
nothing; the build before this release still boots on the upgraded schema, so the SQL can go first and the deploy later; the
rollback below restores the earlier schema exactly; and the new routes answered as they do on H2. Nothing of yours was touched.

## After the deploy

Nothing has to be run by hand, and no run has to be analysed again: a run type and a tag are labels, so nothing about
the effort scores, the zones or the fitness curve depends on them. Every run starts with no type and no tags.

## What behaves differently after deploying

- The run page has a **Run type and tags** card: pick race, long run or workout (or none) and add up to six words of your
  own, up to 24 characters each. The same word in another case counts once.
- A new page, **Training log** (`/training-log`), lists the last 12 weeks, newest first, each as a row with the week's
  runs, distance, time, effort and climb, and the runs by day underneath. It can be filtered by run type and by tags and
  can load earlier weeks (`GET /api/training/log`).
- The Fitness, fatigue and form chart on the Load balance page marks the days of races (`raceDays` in
  `GET /api/training/series`).
- `PATCH /api/activities/{id}` also accepts `runType` and `tags`; `GET /api/activities/{id}/labels` reads them with the
  runner's most used tags. A request with one bad value saves none of its good ones.
- The account export's `runs.csv` has two new last columns, `run_type` and `tags`. Deleting a run deletes its tags, and
  deleting the account deletes all of them.
- `activities` gains one column that is not part of the list of runs.

## Rolling back

Roll the app back first, then (only if you need to) drop what was added:

```sql
DROP TABLE IF EXISTS activity_tag;
ALTER TABLE activities DROP COLUMN IF EXISTS run_type;
```

Leaving them in place is safe for the previous build, because Hibernate's `validate` mode ignores extra columns and
tables. If you roll back for good, drop `activity_tag`: its foreign keys to `activities` and `runner` would block any code
that hard-deletes a run or a runner.
