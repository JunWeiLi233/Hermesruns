# Schema upgrade: goals

This release adds one table. Production runs Hibernate in `validate` mode (`APP_JPA_DDL_AUTO=validate`), so the app **refuses
to boot** until the schema matches. Run the SQL below **before** deploying the new build, and after the earlier upgrades the
same build also needs, if they have not been run yet: [M0](m0-schema-upgrade.md), [M1](m1-schema-upgrade.md),
[M3](m3-schema-upgrade.md) and [M5](m5-schema-upgrade.md). Local H2 databases (`ddl-auto=update`) need nothing.

## The change

```sql
BEGIN;

-- A target a runner set for a week, a month or a year: period is WEEK, MONTH or YEAR; metric is DISTANCE, TIME, COUNT or
-- ELEVATION; target is in the metric's own unit (km, seconds, runs, metres). A runner has at most one goal for each
-- period and metric. What the runner has done towards a goal is never stored: it is added up from their runs when read.
CREATE TABLE IF NOT EXISTS goal (
    id         bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    runner_id  bigint           NOT NULL REFERENCES runner (id),
    period     varchar(8)       NOT NULL,
    metric     varchar(12)      NOT NULL,
    target     double precision NOT NULL,
    created_at timestamp(6)     NOT NULL,
    updated_at timestamp(6)     NOT NULL,
    CONSTRAINT uk_goal_runner_period_metric UNIQUE (runner_id, period, metric)
);
CREATE INDEX IF NOT EXISTS idx_goal_runner ON goal (runner_id);

COMMIT;
```

The statements are idempotent, so running them twice is harmless. The definitions were taken from the JPA mapping (`Goal`),
not written by hand. Types matter: `validate` rejects `real` for the target (it is a `double`) and `timestamp` without a
precision for a `LocalDateTime`.

Checked on 2026-10-10 on a throwaway PostgreSQL 17.10 (the schema this build expects, minus what this document adds, so
not on a copy of production): this build refuses to boot with `validate` before the SQL and boots after it; the result is
Hibernate's own schema apart from the order of the columns and the name of the one foreign key; running it twice changes
nothing; the build before this release (M5) still boots on the upgraded schema, so the SQL can go first and the deploy
later; the rollback below restores the earlier schema exactly; and the goal routes answered as they do on H2 (sixteen
checks: set, refuse a second goal for the same period and metric, change a target, delete, what a named run adds, the
export, and another runner seeing none of it). Nothing of yours was touched.

## After the deploy

Nothing has to be run by hand. A runner starts with no goals; nothing is worked out in advance.

## What behaves differently after deploying

- A **Goals** card on the Profile page and on the Training log page: set a weekly, monthly or yearly goal for distance, time,
  number of runs or climb, and see how far along it is, whether the pace so far is on track, what each remaining day must
  bring, and how the period before went (`GET`, `POST /api/goals`, `PUT`, `DELETE /api/goals/{id}`).
- The run page has a **Goals** card saying what the run adds to each goal (`GET /api/goals?runId=`).
- The account export has a new file, `goals.csv`. Deleting the account deletes the goals.

## Rolling back

Roll the app back first, then (only if you need to) drop what was added:

```sql
DROP TABLE IF EXISTS goal;
```

Leaving it in place is safe for the previous build, because Hibernate's `validate` mode ignores extra tables. If you roll back
for good, drop it: its foreign key to `runner` would block any code that hard-deletes a runner.
