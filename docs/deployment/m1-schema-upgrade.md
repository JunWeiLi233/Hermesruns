# Schema upgrade: effort score and heart-rate zones

This release adds one column and two tables. Production runs Hibernate in `validate` mode
(`APP_JPA_DDL_AUTO=validate`), so the app **refuses to boot** until the schema matches. Run the SQL below **before**
deploying the new build, after [the earlier upgrade](m0-schema-upgrade.md) if that has not been run yet. Local H2
databases (`ddl-auto=update`) need nothing.

## The change

```sql
BEGIN;

-- How hard the runner says a run felt, 1 to 10. The effort score uses it when there is no heart-rate stream.
ALTER TABLE activities ADD COLUMN IF NOT EXISTS perceived_exertion integer
    CONSTRAINT ck_activities_perceived_exertion CHECK (perceived_exertion BETWEEN 1 AND 10);

-- Heart-rate zone boundaries a runner set by hand. A runner without a row gets the automatic zones.
CREATE TABLE IF NOT EXISTS runner_training_zones (
    id               bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    runner_id        bigint       NOT NULL REFERENCES runner (id),
    hr_boundary1_bpm integer,
    hr_boundary2_bpm integer,
    hr_boundary3_bpm integer,
    hr_boundary4_bpm integer,
    hr_source        varchar(8)   NOT NULL,
    created_at       timestamp(6) NOT NULL,
    updated_at       timestamp(6) NOT NULL,
    CONSTRAINT uk_runner_training_zones_runner UNIQUE (runner_id)
);

-- What Hermes worked out about one run: its effort score and its time in each heart-rate zone.
CREATE TABLE IF NOT EXISTS activity_training_metrics (
    id                      bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    activity_id             bigint           NOT NULL UNIQUE REFERENCES activities (id),
    runner_id               bigint           NOT NULL REFERENCES runner (id),
    local_date              date             NOT NULL,
    effort_score            double precision,
    effort_source           varchar(16),
    hr_effort               double precision,
    pace_effort             double precision,
    hr_zone1_seconds        integer,
    hr_zone2_seconds        integer,
    hr_zone3_seconds        integer,
    hr_zone4_seconds        integer,
    hr_zone5_seconds        integer,
    hr_covered_seconds      integer          NOT NULL,
    max_hr_used             integer          NOT NULL,
    hr_boundary1_bpm        integer          NOT NULL,
    hr_boundary2_bpm        integer          NOT NULL,
    hr_boundary3_bpm        integer          NOT NULL,
    hr_boundary4_bpm        integer          NOT NULL,
    perceived_exertion_used integer,
    model_version           integer          NOT NULL,
    stale                   boolean          NOT NULL,
    computed_at             timestamp(6)     NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_atm_runner_date   ON activity_training_metrics (runner_id, local_date);
CREATE INDEX IF NOT EXISTS idx_atm_runner_source ON activity_training_metrics (runner_id, effort_source);

COMMIT;
```

The statements are idempotent, so running them twice is harmless. The column and table definitions were taken from
the JPA mappings (`Activity`, `RunnerTrainingZones`, `ActivityTrainingMetrics`), not written by hand. The `integer`
type for `perceived_exertion` matters: `validate` rejects `smallint` for a field mapped as an integer.

## After the deploy

Nothing has to be run by hand. Every run's effort score and zone times are worked out the first time the run is opened,
when it is imported, and in the background after every start: up to 500 runs per start, newest first
(`app.training.catchup-on-startup`, `app.training.catchup-max-runs`). To work out everyone's history at once, or to redo it
after the model changes, an administrator can start the job:

```
POST /api/admin/jobs/training-metrics-recompute
{"runnerId": 123, "force": true}      both fields are optional; without runnerId it covers every runner with runs
```

It appears in the administrator's job list as `TRAINING_METRICS_RECOMPUTE`.

## What behaves differently after deploying

- The run page shows an **Effort** score and a **Heart-rate zones** breakdown, and the run can be given a 1–10 rating
  (`PATCH /api/activities/{id}`).
- Settings has a **Training zones** section: max heart rate and the five zone boundaries
  (`GET` and `PUT /api/training/zones`). Changing them redoes the effort and zone times of every past run in the
  background.
- `PATCH /api/coach/profile` with a new `maxHeartRateBpm` now also moves the zones, because it is the same field.
- GPX files written the standard way (heart rate and cadence inside `<extensions>`) now keep their heart rate and
  cadence on import. Before this release they were dropped, so GPX runs imported earlier have no heart rate to analyse;
  delete and import them again to get it.
- New runs from Strava are computed twice: when the run is saved, and again when its heart-rate stream arrives.

## Rolling back

Roll the app back first, then (only if you need to) drop what was added:

```sql
DROP TABLE IF EXISTS activity_training_metrics;
DROP TABLE IF EXISTS runner_training_zones;
ALTER TABLE activities DROP COLUMN IF EXISTS perceived_exertion;
```

Leaving them in place is safe for the previous build, because Hibernate's `validate` mode ignores extra columns and
tables. If you roll back for good, drop `activity_training_metrics` and `runner_training_zones`: their foreign keys to
`activities` and `runner` would block any code that hard-deletes a run or a runner.
